# Cache and Parquet baseline

[Hosted run 39730218894](https://github.com/STEVVVU/parquet-io-service/actions/runs/39730218894) measured source `7e5dc9a2a476fd5ec2c887fac13dffcd022e1e81`. Artifact `parquet-benchmark-39730218894` retains the complete request CSVs, commands, fixture/binary hashes, logs and resource snapshots. The result manifest SHA-256 is `9a429862e55c72da64cec64ed14876a58766238618d6e3f942e668a78e60d90c`.

The Ubuntu runner used Linux 7.0.0-1017-azure, glibc 2.39, AMD EPYC 7763, two assigned physical cores/four logical CPUs and Rust 1.99.1 release builds. The actual AWS SDK fetched deterministic Parquet objects from an owned loopback HTTP origin using dummy credentials. Each object contains 16 Int64 columns generated in 8192-row batches. The cache budget was 512 MiB. Each comparison uses a new storage process/cache; warm trials prime the cache before the offered workload. Cache-empty does not mean the OS page cache was evicted.

All 753 trials completed with 97,260 offers: 33,551 successful requests, 63,709 rejections at the consumer's concurrency cap and zero HTTP/decode/correctness errors. Every successful decoded cell was checked against its source formula. A primary audit checked all 97,260 CSV records against receipts, unique offer indices, statuses, expected selected row counts and stable sums. All warm/direct trials fetched zero origin objects; every cache-empty trial fetched at least one. The receipt confirms owned processes stopped and scratch was removed.

## Offered load and stability

The sustained case uses 100,000 rows, maximum row group 65,536, all 16 columns/all groups, eight consumer permits and a 16,014,061-byte object. Ten-second comparisons have five reversed-order repetitions. Values are median [minimum, maximum] of per-trial outcomes. The 60-second rows are single stability trials, with no repeated-run spread claimed. Response latency includes scheduler lag, full-object download, decoding and exact validation for successful requests; rejected offers have no fabricated latency.

At 50 offers/s, warm-cache median download p50 was 198.13 ms [193.56, 198.91], versus decode/validation p50 27.38 ms [26.89, 28.66]. Direct-file decode/validation p50 was 12.23 ms [9.44, 12.66]. At 500 offers/s, warm generator-lag p99 was 2.86 ms [2.44, 3.07], but 4,667 of 5,000 offers were rejected at the eight-permit cap in the median trial. This establishes saturation of the combined consumer/service path under that cap, not a standalone service capacity guarantee.

The 60-second cache-empty/warm/direct trials completed 2,003/1,922/3,000 of 3,000 offers, rejecting 997/1,078/0. Warm successful-response p50/p95/p99 were 236.49/257.87/267.32 ms; direct-file values were 13.42/14.40/14.87 ms. No request error or process failure occurred. No restart/durability test was performed. Across the entire campaign, maximum sampled VmRSS was 53.13 MiB for the server, 322.02 MiB for the consumer and 145.80 MiB for the Python origin/orchestrator. These are periodic snapshots, not measured process high-water marks. Server and client both accumulated substantial system CPU during sustained HTTP traffic; a separate syscall profile is required before attributing that overhead or changing buffering.

## Scope and next diagnosis

Projection and first-row-group selection happen after full-object HTTP download. For the 100k-row object, each successful HTTP request downloads all 16,014,061 bytes regardless of selecting one versus sixteen columns or first versus all groups. Warm storage eliminates origin GETs, but still serves and writes the full object for every request. At one million rows with row groups of 65,536, one-column direct-file decode p50 was about 5.34 ms, while warm HTTP download p50 was about 832.41 ms. The measured limiting stage is the full-object HTTP/temp-file path; stage times alone cannot divide its cost between server reads, network transfer and consumer writes.

This is a loopback origin experiment, not live AWS latency/bandwidth, server pushdown, spill support or a general cache speedup. The fixed generator cap, shared runner and validation cost are part of its scope. Preserve the complete workload and exact correctness checks on any rerun. Profile server and consumer separately before a cause-dependent performance fix.

Reproduce with `cargo +1.99.1 build --release --locked --jobs 2 -p storage-node --example verify_server -p parpulse-client --example benchmark`, then `python3 tools/benchmark_parpulse.py --output .audit/benchmark/run`. The maintained workflow is `.github/workflows/benchmark.yml`. Keep generated run evidence outside Git.
